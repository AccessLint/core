Why is @accesslint/core faster?

@accesslint/core runs at a median of 50 ms per page vs axe-core’s 614 ms — roughly 12× faster across 5,000 sites. The difference comes from architectural choices in how each tool traverses the DOM, schedules work, and computes color contrast.

1. No virtual DOM layer

Before running any rules, axe-core builds a flattened virtual DOM tree. The flattenTree function walks every element in the document, creates a VirtualNode wrapper for each one, resolves Shadow DOM slot assignments, and builds a selector index (an inverted map of tag names, attributes, and IDs for fast lookup). This is an O(n) pass over the entire DOM before any accessibility checks begin.

@accesslint/core skips this entirely. Rules query the live DOM directly with querySelectorAll or TreeWalker, targeting only the elements they need. There is no upfront cost proportional to total DOM size.

2. Synchronous execution vs async scheduling

axe-core uses an async queue system with setTimeout(resolve, 0) between rule completions to yield to the browser event loop. This prevents long-running audits from freezing the UI in a browser extension context. However, each setTimeout has a minimum delay (typically 1–4 ms depending on the browser), and this overhead applies to every rule even in headless environments where there is no UI to keep responsive.

@accesslint/core runs all rules in a single synchronous loop:

for (const rule of activeRules) {
  violations.push(...rule.run(doc));
}

No promises, no timers, no yielding. In automated environments like Playwright (where the benchmark runs), this eliminates scheduling overhead entirely. For browser extension use, @accesslint/core provides a separate createChunkedAudit API that processes rules in time-boxed batches, keeping the fast path as the default.

3. Color contrast: ancestor walk vs spatial grid

Color contrast is the most expensive check in both tools because it requires layout information (getComputedStyle, getBoundingClientRect) which forces the browser to resolve styles and layout.

axe-core builds a spatial grid to determine what sits behind each text element. The createGrid function walks every element in the document with a TreeWalker, calls getBoundingClientRect() on each, assigns them to 200px grid cells, and computes CSS stacking contexts. This is thorough — it correctly handles overlapping elements, z-index, positioned elements, and blend modes — but the grid build itself is an expensive O(n) pass that must touch every element.

@accesslint/core takes a simpler approach: for each text node, it walks up the ancestor chain looking for the first non-transparent background-color, caching results in a WeakMap. This misses some edge cases (text overlapping a non-ancestor element with a background), but it avoids the cost of building a spatial index. When it detects unreliable situations — background images, CSS filters, mix-blend-mode, opacity stacking — it skips the element rather than attempting a potentially wrong answer.

4. Bundle size and parse time

Tool Minified size Dependencies
axe-core 4.11.1 548 KB Bundles Color.js (~2,800 lines)
@accesslint/core 141 KB None

In the benchmark, both scripts are injected via page.addScriptTag() on every site, so the parse-time difference is paid 5,000 times. JavaScript parse time scales roughly linearly with code size, and on a CI runner with constrained CPU this adds up.

5. Frame handling

axe-core includes a full cross-frame messaging protocol. For each <iframe> on the page, it sends a postMessage ping (with a 500 ms timeout), waits for a response, then sends the audit command and waits for results. Even on pages with no iframes, it searches the virtual tree for frame and iframe elements to detect them.

@accesslint/core audits the current document only. It has rules that check attributes on <iframe> elements (like title), but does not crawl into iframe content or use cross-frame messaging. In the benchmark’s Playwright environment, frames are navigated to separately if needed.

6. Shared caches across rules

Both tools cache computed values, but @accesslint/core’s caches are designed to be shared across rules within a single audit. Seven WeakMap-based caches cover the most expensive repeated operations:

  • isAriaHidden — walks ancestors checking aria-hidden, hidden, display:none
  • getComputedRole — resolves explicit or implicit ARIA role
  • getAccessibleName — implements the accessible name computation
  • getComputedStyle — caches window.getComputedStyle() calls
  • getEffectiveBackgroundColor — caches ancestor-chain background resolution
  • mayBeOverImage — caches detection of text positioned over images
  • getSelector — caches CSS selector generation for violation reporting

Because rules run synchronously in sequence, a cache populated by an early rule (e.g., isAriaHidden computed during the ARIA rules) is immediately available to later rules (e.g., color-contrast). All caches are cleared between audits to prevent stale data.

7. Fewer rules, narrower scope

axe-core ships 174 rules. @accesslint/core ships 93. axe-core covers best practices, experimental rules, and Section 508 mappings beyond WCAG. @accesslint/core focuses on WCAG 2.1 Level A and AA success criteria. Fewer rules means less work per audit, but the rule count alone doesn’t explain the 12× difference — the architectural choices above are the primary factors.

Tradeoffs

These performance gains come with tradeoffs:

  • No iframe content traversal — @accesslint/core checks attributes on <iframe> elements but does not audit content inside them.
  • Simpler contrast model — the ancestor-walk approach does not detect contrast issues caused by non-ancestor overlapping elements (e.g., an absolutely positioned box behind text).
  • No Shadow DOM flattening — rules query the light DOM directly. Elements inside Shadow DOM are detected and skipped rather than audited.
  • Synchronous by default — on a page with a very large DOM, the synchronous audit could block the main thread. The createChunkedAudit API mitigates this for browser contexts.

For automated testing and browser extension use — the primary use cases for @accesslint/core — these tradeoffs are acceptable. The goal is fast, actionable results on the most common accessibility issues.
